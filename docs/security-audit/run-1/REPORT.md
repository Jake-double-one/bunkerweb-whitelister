## 1. Run facts

- Scope: the whole repository at `/home/user/bunkerweb-whitelister`, source ref `033b4ce0b6a79a0054cbf21f6a34beb7b969e739` (clean worktree).
- Budget: none set. Agents spent: 24 hunter/verifier assignments plus 4 reconnaissance agents and 4 coverage critics.
- Execution policy: sandboxed-source-and-local-only. Every target-controlled check ran inside an OS-enforced sandbox (user+mount+network namespaces, no external network, loopback only, read-only target and toolchain, empty allow-listed environment, scratch-only writes, CPU/memory/process/file/wall-clock limits); evidence files were promoted by trusted parent-side code with the no-follow, bounded-size procedure. - Deferred / out-of-scope coverage: none. Ledger status: {'covered': 19, 'candidate': 5}. The final-clean critic accepted no missing units and no reassignments.

## 2. Security posture

The application's trust boundaries hold against every lower-trust principal examined: anonymous internet clients cannot bypass the password (constant-time compare / full PBKDF2 off the event loop, per-client and global throttling, cross-site posts refused without counting), cannot forge or revive sessions (signed cookie plus server-side session row, `__Host-`/HttpOnly/SameSite=Strict, revocation on logout), cannot cross-site-request state changes (per-session CSRF token plus Sec-Fetch-Site/Origin checks), cannot spoof the client address past a trusted proxy (right-to-left X-Forwarded-For walk, unparsable chain refuses login), cannot read `/ips.txt` through the proxy, and cannot inject into SQL, HTML, the audit log, the API path or the inline style. Dependencies are hash-pinned, the image runs non-root without pip, and CI publication is gated to main and version tags.

The two confirmed findings are both **low** and both concern a logged-in operator (the holder of the single shared password) bypassing the container operator's entry policy rather than any authentication or isolation control: an IPv6 scope id can smuggle extra lines into the plain list, and entries stored under an earlier, more permissive policy survive and can be revived or made permanent through the extend path. Three leads need owner-observed facts about BunkerWeb and the deployment: the example compose trusts a whole shared subnet as proxy, a cache-name mismatch (which the shipped example itself produces when the LIST_TOKEN recommendation is followed) is reported as success, and one storage error silently stops the background expiry loop.

### LOW — Entry policy tightening is not applied to stored rows: a password holder keeps, revives and makes permanent networks the current MIN_PREFIX_*/ALLOW_PRIVATE policy forbids

Fingerprint: `whitelister/app.py:extend_entry:stored-network-not-revalidated`

**Source location.** whitelister/app.py extend_entry fetches the row with store.get (app.py:440) and writes the new expiry with store.set_expiry (app.py:461) without passing entry.network through parse_network(..., settings); duration=forever (app.py:445-446) removes the expiry outright and _extend_from (app.py:529-533) treats an expired row as extendable from now. ips_txt (app.py:302) and EntryStore.active_networks (entries.py:211-217) select by expiry only. EntryStore.__init__ (entries.py:107-126) and create_app (app.py:96-134) perform no re-validation of existing rows when settings change, so the policy is enforced exclusively at insertion time (the single parse_network call site, app.py:410).

**Lower-trust principal.** A password holder notices that the operator tightened the entry rules (adding 10.0.0.0/8 or a private range is now refused) but that previously added rows are still listed on the page. Using the extend control on those rows they keep them active, bring an expired one back, or set them to forever, so the whitelist keeps networks the operator intended to no longer allow.

**Bounded reproduction (target-native).**
1. Run the app in-process with httpx.ASGITransport(app, client=('10.0.0.2', 12345)) against a file-backed SQLite store in a scratch DATA_DIR, with WHITELISTER_PASSWORD, SESSION_SECRET, COOKIE_SECURE=no, TRUSTED_PROXIES=none, LIST_ALLOWED_NETWORKS=10.0.0.0/8, TZ=UTC and no BW_API_URL (API disabled, refresh_after_change is a no-op).
2. Phase A: load_settings + create_app with ALLOW_PRIVATE=yes MIN_PREFIX_V4=8; POST /login, read the _csrf token from GET /, POST /entries for 10.0.0.0/8 (30 days) and 192.168.50.0/24 (1 day); after the lifespan closes, reopen EntryStore on the same file and set the /24 row's expires_at to two hours ago via set_expiry (an expired-but-retained row).
3. Phase B: new load_settings + create_app on the same DATA_DIR with ALLOW_PRIVATE=no MIN_PREFIX_V4=16; GET /ips.txt; log in; POST /entries for 10.0.0.0/8, 192.168.50.0/24 and 192.168.50.1 and decode the wl_flash cookie of each 303 (itsdangerous URLSafeTimedSerializer, salt 'whitelister.flash').
4. POST /entries/<id of /24>/extend duration=14, POST /entries/<id of /8>/extend duration=forever, POST /entries/<id of /24>/extend duration=forever; decode the flash after each and read the rows' expires_at; control: POST /entries/999/extend; GET /ips.txt again; call store.purge_expired(now + 20 years).
5. Compare: the add path refuses both networks, the extend path accepts them, /ips.txt serves both, purge removes nothing.

Payloads:
- `POST /entries  network=10.0.0.0/8  label=dummy  duration=30  _csrf=<token>   (phase A, ALLOW_PRIVATE=yes MIN_PREFIX_V4=8)`
- `POST /entries  network=192.168.50.0/24  label=dummy  duration=1  _csrf=<token>   (phase A; then its expires_at moved 2 h into the past to make it expired-but-retained)`
- `POST /entries  network=10.0.0.0/8  duration=7  _csrf=<token>   (phase B, ALLOW_PRIVATE=no MIN_PREFIX_V4=16: refused)`
- `POST /entries  network=192.168.50.0/24  duration=7  _csrf=<token>   (phase B: refused)`
- `POST /entries/2/extend  duration=14  _csrf=<token>   (phase B: revives the expired private /24)`
- `POST /entries/1/extend  duration=forever  _csrf=<token>   (phase B: makes the /8 permanent)`
- `POST /entries/2/extend  duration=forever  _csrf=<token>   (phase B: makes the /24 permanent)`
- `GET /ips.txt  from TCP peer 10.0.0.2 with no forwarding headers`

**Conditions.**
- authentication_level: Attacker is a logged-in operator (holder of the single shared password) with a valid session and CSRF token; this principal is bounded by, but cannot change, the container operator's entry policy.
- system_configuration: The container operator tightened MIN_PREFIX_V4/V6 or set ALLOW_PRIVATE=no (or otherwise tightened parse_network) after rows had been accepted under the earlier permissive settings, and did not manually delete those rows.
- data_state: A row for the now-forbidden network exists in the SQLite entries table: active (extendable / forever) or expired within EXPIRED_RETENTION_DAYS (default 7) so it has not yet been purged and can be revived.

**Actual result.** Verifier run (sandbox, python 3.13.17, 2026-10-29 13:24 UTC). Phase A (allow_private=True min_prefix_v4=8): POST /entries 10.0.0.0/8 -> 303 'info: 10.0.0.0/8 is allowed until 2026-11-28 13:24.' (id=1); 192.168.50.0/24 -> 303 'info: ... allowed until 2026-10-30 13:24.' (id=2, then set expires_at=2026-10-29 11:24:33 UTC). Phase B (allow_private=False min_prefix_v4=16, same SQLite file): GET /ips.txt -> 200 '# bunkerweb-whitelister\n10.0.0.0/8\n'. POST /entries 10.0.0.0/8 -> 303 flash 'alert: Networks must be /16 or smaller.'; 192.168.50.0/24 and 192.168.50.1 -> 'alert: Private addresses are not allowed here.'. POST /entries/2/extend duration=14 -> 303 'info: 192.168.50.0/24 now runs until 2026-11-12 13:24.' (expires_at 2026-11-12 13:24:33 UTC, revived from expired). POST /entries/1/extend duration=forever -> 303 'info: 10.0.0.0/8 now never expires.' expires_at=None. POST /entries/2/extend duration=forever -> 303 'info: 192.168.50.0/24 now never expires.' expires_at=None. Control POST /entries/999/extend -> 'alert: That entry no longer exists.'. GET /ips.txt -> 200 '# bunkerweb-whitelister\n10.0.0.0/8\n192.168.50.0/24\n'. purge_expired(now+20y) removed [] ; active_networks = ['10.0.0.0/8', '192.168.50.0/24']. Transcript: scratch/check-1-v3-7-repro.txt (not promoted by the verifier).

**Impact.** The password holder cannot add new forbidden networks; they can only keep, revive (within EXPIRED_RETENTION_DAYS) or make permanent networks that were previously allowed. Those networks (demonstrated: a /8 and a private /24) remain on the list BunkerWeb trusts and skips checks for, contrary to the current policy, until the container operator deletes them. No disclosure, no new principal, no escalation beyond the operator's existing whitelist authority.

**Priority rationale.** Likelihood low: Requires a prior permissive period, a later tightening of MIN_PREFIX_*/ALLOW_PRIVATE by the container operator who did not also delete the affected rows, and a password holder who wants to keep them; the rows and every extend remain visible on the page and in the JSON audit log (entry.extend with network and expires_at), so the drift is detectable. Impact low. Overall low. Confidence high: Complete source lineage (single parse_network call site at app.py:410, no startup re-validation, expiry-only selection in active_networks and purge_expired) and an independent in-process reproduction by the verifier on a file-backed store across a settings change, with the add path refusing and the extend path accepting the identical networks, and /ips.txt serving them.

**Smallest source fix.** Re-apply the current entry policy to the stored network on every path that keeps or makes a row active. Required: in extend_entry call parse_network(entry.network, settings) inside the existing try block so a row that fails the current policy is refused with the same alert flash as the add form (the operator must delete it or the container operator must re-permit it); this closes the demonstrated extend/revive/forever path. Recommended in addition, because an already-active forbidden row is still served until it expires: add EntryStore.policy_violations(settings), log a warning for each at startup in the lifespan, and either exclude those rows from active_networks (so /ips.txt matches the policy immediately) or surface them in the UI for deletion. Regression test: create 10.0.0.0/8 with MIN_PREFIX_V4=8 on a file-backed store, rebuild the app on the same DATA_DIR with MIN_PREFIX_V4=16, POST /entries/{id}/extend with duration=14 and duration=forever, and assert the 303 carries the prefix_too_wide alert and expires_at is unchanged (the two apps must not share one EntryStore object: the first lifespan closes it).

### LOW — IPv6 scope id with an embedded newline passes parse_network and is written verbatim to /ips.txt, letting a logged-in operator list addresses the entry policy refuses

Fingerprint: `whitelister/entries.py:network_text:ipv6-scope-id-newline-into-ips-list`

**Source location.** whitelister/entries.py network_text() serialises a single-host IPv6 network with str(net.network_address) (and an aligned IPv6 network with str(net)), which includes the RFC 4007 scope id; ipaddress.ip_network in parse_network accepts a scope id containing newline, carriage return, NUL, '#' or any character other than '%'. Neither parse_network nor render_list rejects scope ids or checks that each emitted list line is a single address token, so the per-line policy enforced on the parsed object does not apply to the text actually written.

**Lower-trust principal.** A person holding the whitelister password (any logged-in operator) wants to whitelist a host that the deployment's entry policy refuses, e.g. a loopback host or, under ALLOW_PRIVATE=no, a private host, or wants to append arbitrary lines to the list BunkerWeb downloads.

**Bounded reproduction (target-native).**
1. Run the app with default entry settings (TRUSTED_PROXIES=10.0.0.0/8, COOKIE_SECURE=no, SESSION_SECRET of >= 32 chars, WHITELISTER_PASSWORD of >= 12 chars, a fake BunkerWeb API or no BW_API_URL) and send requests from a peer inside LIST_ALLOWED_NETWORKS, e.g. 10.0.0.2.
2. POST /login with the password; GET / and read the hidden _csrf value from the form.
3. Control: POST /entries with network=127.0.0.1, duration=7 and the token; confirm no entry row exists and GET /ips.txt (no forwarding headers) returns only '# bunkerweb-whitelister'.
4. POST /entries with network='2a00::1%x' + newline + '127.0.0.1' (urlencoded 2a00::1%25x%0A127.0.0.1), duration=7 and the token.
5. GET /ips.txt from the allowed peer without forwarding headers and split the body on newline; repeat the control and injection with network=10.0.0.1 / '2a00::1%x\n10.0.0.1' in a deployment started with ALLOW_PRIVATE=no.

Payloads:
- `network=2a00::1%25x%0A127.0.0.1&label=probe&duration=7&_csrf=<token>`
- `network=2a00::1%25x%0A10.0.0.1&label=probe&duration=7&_csrf=<token>  (deployment with ALLOW_PRIVATE=no)`
- `network=2a00::1%25x%0A%23%20injected%0A224.0.0.1&label=probe&duration=7&_csrf=<token>`

**Conditions.**
- authentication_level: Requires a logged-in operator session (knowledge of the shared password) plus the session's CSRF token and a same-origin request; what is bypassed is the configured entry policy, not authentication or CSRF.
- system_configuration: Under the default MIN_PREFIX_V6=48 only single hosts, comment/arbitrary text lines and IPv6 CIDRs with prefix >= 48 can be injected, because a trailing '/n' is applied to the carrier IPv6 address; injecting IPv4 CIDRs such as 10.0.0.0/8 would additionally require MIN_PREFIX_V6 <= 8 (prefix >= MIN_PREFIX_V6).
- third_party_dependency: Whether BunkerWeb actually honours an injected line depends on its whitelist-download job's own per-line parsing; no BunkerWeb source is in the repository and the downstream effect was not observed locally. The demonstrated result ends at the text served by /ips.txt.

**Actual result.** Sandboxed in-process run (httpx.ASGITransport, in-memory EntryStore, MockTransport fake BunkerWeb API, Python 3.13.17, httpx 0.28.1, peer 10.0.0.2): control POST /entries network=127.0.0.1 -> 303, stored rows [], GET /ips.txt -> 200 '# bunkerweb-whitelister\n'. Injection POST /entries network='2a00::1%x\n127.0.0.1' -> 303, stored rows [{'id': 1, 'network': '2a00::1%x\n127.0.0.1', 'label': 'probe'}], GET /ips.txt -> 200 with lines ['# bunkerweb-whitelister', '2a00::1%x', '127.0.0.1']. With ALLOW_PRIVATE=no: direct 10.0.0.1 -> stored rows [], list unchanged; '2a00::1%x\n10.0.0.1' -> 303, one row, /ips.txt lines ['# bunkerweb-whitelister', '2a00::1%x', '10.0.0.1']. The audit line JSON-escapes the newline ('"network": "2a00::1%x\\n127.0.0.1"'). Unit level: parse_network+network_text of '2a00::1%x\n# injected\n224.0.0.1' yields a three-line stored string; '2a00::%x\n10.0.0.0/8' is refused (prefix_too_wide).

**Impact.** Demonstrated effect is limited to the text of /ips.txt: a policy-refused single host (or comment/arbitrary line, or an IPv6 CIDR >= MIN_PREFIX_V6) is served to the BunkerWeb scheduler. No wider-than-MIN_PREFIX IPv4 range can be injected under default configuration, the actor is an authenticated operator, the audit trail still records the full value, and BunkerWeb's acceptance of the injected line was not observed.

**Priority rationale.** Likelihood low: Needs the operator password, a valid session and its CSRF token; that principal is already entitled to whitelist any routable network, so the only thing gained is bypass of the configured refusal of loopback/multicast/unspecified/reserved/private ranges and the ability to add free-text lines. The payload is trivial once logged in. Impact low. Overall low. Confidence high: Independently reproduced end-to-end in the OS sandbox with the pinned interpreter and dependencies: ipaddress scope-id behaviour, parse_network/network_text output, the stored row and the served /ips.txt body were all observed directly, and the trace is complete inside the repository. Only the BunkerWeb-side consequence is unverified and is recorded as a condition.

**Smallest source fix.** Refuse IPv6 scope ids at the parser and make the list writer defensive. In parse_network reject any input containing '%' or interior whitespace before calling ipaddress, and additionally reject a parsed IPv6 network whose network_address.scope_id is not None (scope ids are never meaningful for a reverse-proxy whitelist). In render_list emit only values that are printable, contain no whitespace or '%', and round-trip through ipaddress.ip_network, so rows stored before the fix cannot add lines. Add regression tests: parse_network('2a00::1%x\n127.0.0.1') and parse_network('fe80::1%eth0') raise error.ip_invalid, and every non-header line of render_list output parses as a single network. Verified in the sandbox against the current code: the re-implemented parser refuses all scope-id variants (LF, CRLF, NUL, aligned CIDR) while 1.2.3.4, 203.0.113.42/24, 2a00::1, 2001:db8::/48 and ::ffff:1.2.3.4 are still accepted unchanged, and the defensive render_list drops legacy multi-line rows.

## 5. Hardening notes

Non-findings recorded by the hunters (no reachable boundary violation; worth doing, not security defects). Grouped by file.

**.gitignore**
- .gitignore does not cover .env.* variants (e.g. .env.local, .env.production) or *.key/session.key outside data/; add `.env.*`, `!.env.example`, `*.key`.

**GET**
- GET /ips.txt (whitelister/app.py:300) keeps internet clients out only through a negative signal: has_forwarding_headers (whitelister/security.py:275-276) must see one of five header names that the upstream proxy is assumed to add, while the peer allowlist cannot separate BunkerWeb from the scheduler in the shipped topology (docker-compose.example.yml:16,22,53-57,79-83 put both on 10.20.30.0/24, which .env.example:14,23 lists in both TRUSTED_PROXIES and LIST_ALLOWED_NETWORKS) and LIST_TOKEN is off by default. Verified locally that via, x-client-ip, true-client-ip, cf-connecting-ip and x-forwarded-port are not treated as forwarding headers (check-1 A5, check-3 R7/R8). Suggested: include settings.client_ip_header in has_forwarding_headers, and either require LIST_TOKEN or log a startup warning when LIST_ALLOWED_NETWORKS overlaps TRUSTED_PROXIES; regression test: a request from a trusted-proxy peer carrying only CLIENT_IP_HEADER must get 403.

**LIST_TOKEN_FILE**
- LIST_TOKEN_FILE pointing at an empty or whitespace-only file yields list_token == '' (whitelister/config.py:32-43,213), which passes the `is None` test at whitelister/app.py:299 and makes _const_eq('', '') succeed, so /ips.txt is served with no ?token= at all (check-1 D1) while the operator believes a token is enforced. Suggested: raise ConfigError when LIST_TOKEN or its _FILE resolves to an empty string.

**Observed**
- Observed as input to the rendering unit, acceptance owned by the parse_network/render_list peer units: ipaddress accepts IPv6 scope ids containing arbitrary characters except '%' and '/', so POST /entries stores 'fe80::1%<svg onload=alert(3)>' verbatim and a trusted-proxy X-Forwarded-For can yield a client_ip of 'fe80::2%<img src=x onerror=alert(4)>'. All HTML sinks escape it and the audit log is JSON, but stripping or rejecting scope ids in entries.py:parse_network and security.py:parse_ip would keep network strings in a plain IP/CIDR alphabet for the /ips.txt line and logs.

**Pre-auth**
- Pre-auth requests with a non-integer entry id return FastAPI's pydantic 422 JSON (framework fingerprint); add a RequestValidationError handler that returns a plain 404/400.

**Sessions**
- Sessions issued under an old WHITELISTER_PASSWORD remain valid after the password is rotated (env change + restart keeps /data sessions and SESSION_SECRET): observed locally in check-3.txt. README.md:57 documents SESSION_SECRET rotation as the global logout; consider stating that password rotation must be paired with SESSION_SECRET rotation, or mixing a fingerprint of the configured password/hash into the SessionCodec key (security.py:86-90) so a credential change ends every session.

**When**
- When a client's own address is inside TRUSTED_PROXIES, the all-hops-trusted fallback at whitelister/security.py:268-269 takes the leftmost hop, so that host can choose the address used for the login throttle key, audit 'client' and created_by (check-2 W1/W2 with TRUSTED_PROXIES=10.0.0.0/8, peer 10.5.5.5 shown as 10.9.9.9 or 203.0.113.77). This is the documented meaning of a trusted proxy, but the tests and .env.example invite wide ranges; suggested: warn at startup when TRUSTED_PROXIES is wider than the proxy's actual subnet(s) or equals LIST_ALLOWED_NETWORKS, and state in .env.example that every host in TRUSTED_PROXIES can set its own identity.

**general**
- README.md:76 says 'no pip at runtime' but Dockerfile:9 creates /opt/venv with pip (venv default) and only the base interpreter's pip is removed at line 28; use `python -m venv --without-pip /opt/venv` and install with the base pip via `--python /opt/venv/bin/python`, or run `/opt/venv/bin/pip uninstall -y pip` at the end of the build stage.
- The image job (ci.yml:34-40) carries packages:write and security-events:write for every branch push and PR although only main/v* runs use them; move login/metadata/push into a separate job with a job-level `if:` so branch and PR runs hold a read-only token. Branch/tag protection for main and v* tags (tag rulesets) is a hosted setting the owner should confirm, since any v* tag push publishes semver and latest tags.

### Positive source patterns

- Password check always runs the full PBKDF2 or a constant-time compare; hashing is bounded to two concurrent checks off the event loop; cross-site login posts are refused before any accounting.
- Sessions are both signed and server-side (revocable); CSRF token is per session and compared in constant time; Sec-Fetch-Site and Origin are checked as well.
- Uvicorn's own proxy-header handling is disabled so one resolver decides; `TRUSTED_PROXIES` is a mandatory decision; repeated forwarding headers are joined, not first-wins.
- Every SQL statement is parameterised; Jinja autoescape plus StrictUndefined; strict CSP with a per-request nonce; no inline styles or scripts; self-hosted fonts.
- Hash-pinned dependencies with `--require-hashes` in both image and CI; non-root uid 10001; read-only, cap-dropped compose example; GHCR push gated to main/v* tags.
