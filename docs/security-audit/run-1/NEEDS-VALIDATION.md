## Compose example trusts the whole shared bw-services subnet as reverse proxy and list reader

Fingerprint `docker-compose.example.yml:whitelister:TRUSTED_PROXIES:shared-bw-services-subnet`

docker-compose.example.yml (the file README's quick start deploys) attaches the whitelister to BunkerWeb's bw-services network and sets TRUSTED_PROXIES to that entire /24 instead of the BunkerWeb ingress address; .env.example additionally allows /ips.txt from both subnets and leaves LIST_TOKEN unset. Any other container on bw-services, which in BunkerWeb's standard topology is every backend application the proxy publishes, is therefore treated as the ingress: it can connect to port 8080 directly (bypassing BunkerWeb's /login 6r/m limit and WAF), choose the client identity by setting X-Forwarded-For, which defeats the per-client login lock (only the process-wide 30 failures/minute budget remains) and forges the address in every audit line, and read the live whitelist from /ips.txt without any token. The application logic behaves as designed; the weakness is the deployment scope of the trusted-proxy and list-reader networks. Whether a lower-trust workload actually shares bw-services in the owner's stack is not visible in source.

**Claimed root cause.** docker-compose.example.yml:16 and .env.example:14 define TRUSTED_PROXIES as the full bw-services subnet (10.20.30.0/24) that the whitelister joins at docker-compose.example.yml:22, rather than the single BunkerWeb ingress address or a dedicated proxy-only network, and .env.example:23-26 allow list downloads from the same shared subnets without the recommended LIST_TOKEN; config.py:192 turns that into a network allowlist that security.py:254-259 honours for any peer in it.

## A WHITELIST_URL that differs from WHITELIST_IP_URLS turns every revocation into a cache miss that the app reports as success; the example compose produces exactly that mismatch when the .env.example LIST_TOKEN recommendation is followed

Fingerprint `whitelister/bunkerweb.py:BunkerWebClient._trigger:persistent-404-jobs-run-reported-as-ok+compose-WHITELIST_URL-override`

## One storage error in a Syncer tick permanently and silently stops expiry-driven BunkerWeb invalidation while /healthz stays ok and the UI shows only 'Refresh pending' or 'API connected'

Fingerprint `whitelister/bunkerweb.py:Syncer._run:unguarded-store-call-silently-ends-expiry-propagation`

Syncer._run (whitelister/bunkerweb.py:147-172) is the only code path that turns an entry's expiry into an invalidation request to BunkerWeb; explicit operator add/extend/delete call client.trigger_refresh() directly (app.py:223-232). The tick body calls store.expired_between() (line 160) and store.purge_expired() (line 164) with no exception guard; only client.trigger_refresh() (169-172) is guarded. A sqlite3 error raised by the shared connection on the /data volume (another process writing the database longer than the 5 s busy_timeout at entries.py:113, SQLITE_FULL, an I/O error) propagates out of the coroutine; the single asyncio task (started once at app.py:119-120, kept in self._task, no done-callback, no restart) finishes with the exception, which is never logged (the task stays referenced so asyncio never reports it; Syncer.stop() at bunkerweb.py:140-145 retrieves and swallows it at shutdown). From then on, for the life of the process: entries that reach their end are no longer reported to BunkerWeb, expired rows are never purged, and failed direct refreshes are never retried. GET /healthz (app.py:290-292) is a constant, so the Dockerfile:41-42 and docker-compose.example.yml:33-37 healthchecks keep passing; api_state() (app.py:234-242) reads only client.status, so the header shows 'Refresh pending' (when the failure hits purge_expired after expired_between already set pending=True, the realistic SQLITE_BUSY case under WAL) or 'API connected' (when the failure hits expired_between first, or after any later operator action whose direct refresh succeeds and clears pending). Verifier reproduction in the sandbox with a genuine 'database is locked' from a second connection holding BEGIN IMMEDIATE across the expiry tick (EXPIRED_RETENTION_DAYS=0 so that tick issues its purge DELETE): syncer task done with OperationalError('database is locked'), zero API calls after that entry's expiry and after a second entry's expiry (control run: DELETE /cache/global/whitelist/whitelist-download/<sha1>.list 2.5 s after expiry, entry purged), /healthz 200 {"status":"ok"}, header data-state="pending" 'Refresh pending', client.status.ok=True, last_error=None, no log record above INFO about the failure at runtime or shutdown (the only WARNING records are the two lifespan startup configuration notices for TRUSTED_PROXIES and COOKIE_SECURE), expired row still in the DB. The app's own /ips.txt already omits the expired entry (computed live, entries.py:211-217), so the loss is confined to telling BunkerWeb: the expired network keeps bypassing BunkerWeb's checks until BunkerWeb re-fetches the list on its own. Whether that happens after the documented one-hour download cache (README.md:33-34, bunkerweb.py:3-5) or never is BunkerWeb behaviour absent from the repository. No lower-trust principal of the app can cause the triggering fault: the store uses one in-process connection behind a threading.Lock (entries.py:108-113), all routes run on the event loop, and entries (5000 cap) and sessions are bounded, so the fault requires a container-operator-level or environmental condition on /data.

**Claimed root cause.** whitelister/bunkerweb.py:160 and :164 perform the tick's store calls outside any try/except, and the Syncer has no supervision (single task created at bunkerweb.py:135 with no add_done_callback, no restart, no error flag on SyncStatus, exception swallowed at bunkerweb.py:144), so a single transient storage error becomes a permanent, unreported loss of the expiry-to-invalidation lifecycle contract that README.md:31-32 promises, masked by the constant /healthz (app.py:292) and an api_state() (app.py:234-242) that never reflects the task's liveness.

Whether the whitelist-download job re-fetches WHITELIST_IP_URLS on its own schedule once its one-hour cache (bunkerweb.py:3-5, README.md:33-34) is older than one hour, or only re-downloads when the cache file is deleted or the job is run through the API, decides whether an expired network keeps bypassing BunkerWeb's checks for up to about one hour (the same limit the README documents for API-off mode, making this a silent degradation to that mode for expiries only) or indefinitely until the next operator add/extend/delete or a container restart. The app side (no DELETE ever sent after the fault) is fully demonstrated locally; this external fact fixes the impact.
- Likelihood only, owner-observed: how often a storage fault reaches the tick's store calls in the owner's deployment. Source shows no lower-trust trigger (one in-process connection behind a lock, bounded entries and sessions), so the trigger is an external writer on the mounted /data/whitelist.sqlite3 holding a write lock longer than 5 s during a tick that has rows to purge (under WAL a plain writer does not block the tick's SELECTs), a full /data volume at that DELETE, or an I/O error on either query. The same fault hitting an operator request would surface as a 500, but one confined to the background tick is invisible.

### Owner-observed deployment plan
Owner-observed, non-destructive, on a staging BunkerWeb 1.6.17 stack built from docker-compose.example.yml with a throwaway whitelister database: (1) start the whitelister with EXPIRED_RETENTION_DAYS=0 (so the tick after an expiry performs its purge DELETE; with the default 7 days a fresh test entry never makes the tick write under WAL, and an external lock alone will not fail it) and add a test entry for an unused network with a 'date' duration ending at the next end-of-day in TZ (or a 1-day entry and wait). (2) About one minute before that end, from a host shell open sqlite3 on the mounted /data/whitelist.sqlite3, run BEGIN IMMEDIATE; and keep the shell open until at least 40 s after the entry's end (one 30 s tick plus the 5 s busy_timeout), then ROLLBACK; (3) Verify in docker logs: an INFO 'entry expired: <network>' line and no WARNING/ERROR afterwards; docker inspect still reports healthy; the UI header shows 'Refresh pending' (and 'API connected' after any later add/delete); the bw-api access/scheduler log shows no DELETE /cache/global/whitelist/whitelist-download/<sha1>.list and no POST /jobs/run at or after the entry's end. (4) Add a second short test entry and confirm its expiry also produces no API call, while an add/delete by the operator still does. (5) Decisive observation: from the expired test network, send requests through BunkerWeb and record for how long they are still whitelisted; in parallel watch the whitelist-download cache file (GET /cache/global/whitelist/whitelist-download/<sha1>.list with the API user's cache_read permission, or the scheduler log) to see whether BunkerWeb re-downloads /ips.txt on its own once the file is older than one hour. If it does, the stale window is bounded to about one hour; if not, it lasts until the next operator change or restart.
