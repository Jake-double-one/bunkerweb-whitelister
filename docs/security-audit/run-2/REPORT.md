## 2. Security posture

The trust boundaries of the previous run still hold at v0.4.2 for anonymous internet clients: password check, sessions, CSRF, proxy-header resolution, `/ips.txt` gating, SQL/HTML/log/path/style injection, dependency pinning, non-root image and gated CI were all re-examined on the current source and no boundary violation was found. The new anonymous surface, the invitation link, is sound in its core: the token is 24 random bytes compared through a SHA-256 hash, GET has no side effect, POST requires a same-origin fetch, the redeemer's network is derived only from the resolved client identity and re-passes the operator's entry policy, closed and unknown links render the identical 404 page, and the budget is counted by distinct addresses with no way for the guest to choose another address.

All 5 confirmed findings are **low**; four sit on the invitation feature's seams with the operator's own data and with the public rate limiter, one is a robustness defect in the prefill link: a redemption from a network the operator already listed silently rewrites that operator entry (shortens a permanent grant, relabels and re-attributes it); the invite-link throttle shares the login throttle's global budget, so about 30 bad tokens from a handful of addresses lock every invite link for a minute; each free renewal from a known address fires a BunkerWeb cache delete and an event row, so one guest can evict the operator's history and keep the syncer busy; and deleting an invited entry does not forget the address in the invite's address table, so a removed guest re-adds past an exhausted budget as a 'refresh'. The fifth: the prefill link (`/?add=&days=&label=`) lets an over-long label or a non-decimal Unicode digit raise out of the index page as a bare 500 without the security headers, which an anonymous party can make the operator's post-login landing page through `next`. Two leads need owner-observed facts: whether the whitelister's second network attachment (bw-universe) lets BunkerWeb reach it from an address outside `TRUSTED_PROXIES`, and whether the direct `/ips.txt` gate is reachable from outside the proxy in the real deployment.

### LOW — Prefill query values (over-long label, non-decimal Unicode digit days) raise unhandled exceptions out of GET /, producing a header-less 500 that an anonymous next-link can make the operator's post-login landing page

Fingerprint: `whitelister/app.py/prefill_from_query/unhandled-ValidationError-ValueError`

**Source location.** prefill_from_query (whitelister/app.py:253-267) wraps only network_text(parse_network(...)) in try/except ValidationError (lines 260-263). Line 265 guards int(q['days']) with str.isdigit(), which is True for Unicode digit characters such as U+00B2 that are not decimal digits and that int() rejects with ValueError (str.isdecimal() or str.isascii() would be the correct guard). Line 267 calls normalize_label(q.get('label', '')) outside any try, and normalize_label raises ValidationError('error.label_too_long') when the normalised text exceeds MAX_LABEL=64 (whitelister/entries.py:34-35). index() calls prefill_from_query at app.py:492 with no exception handling, and the FastAPI app created at app.py:148 registers no exception handler (FastAPI's defaults cover only HTTPException and RequestValidationError), so both exceptions leave the route, cross SecurityHeadersMiddleware.dispatch at app.py:87 before the headers are added, and are turned into a bare 500 by Starlette's ServerErrorMiddleware. create_invite (app.py:635) repeats the unguarded normalize_label(name) call before its try block at 638.

**Lower-trust principal.** An anonymous party who can get the operator to click a link to the whitelister (e.g. in a message asking for an address to be listed) can make the operator's post-login landing page a bare 500 instead of the prefilled form; the operator recovers by visiting / again. The operator can also trigger it themselves with a hand-edited URL or a crafted POST /invites.

**Bounded reproduction (target-native).**
1. Build the app in-process as tests/conftest.py does: load_settings() with dummy env (WHITELISTER_PASSWORD, SESSION_SECRET, DATA_DIR in a writable scratch dir, COOKIE_SECURE=no, TRUSTED_PROXIES=10.0.0.0/8, BW_API_URL/USERNAME/PASSWORD, WHITELIST_URL, SYNC_DEBOUNCE_SECONDS=0, TZ=UTC), EntryStore(':memory:'), BunkerWebClient whose _client uses an httpx.MockTransport fake bw-api, and httpx.AsyncClient over httpx.ASGITransport(app, client=('10.0.0.5', 40000), raise_app_exceptions=False) with header X-Forwarded-For: 203.0.113.9.
2. POST /login with the dummy password (303 to /); GET /?add=me&days=7&label=Laptop and record status 200 and the Content-Security-Policy, X-Frame-Options, Cache-Control and X-Content-Type-Options headers (baseline); GET /?add=me&label=<64 x 'a'> as the boundary control (expect 200).
3. In the same logged-in client GET /?add=me&label=<65 x 'a'> and GET /?add=me&days=%C2%B2; record status and which of the four headers are present. GET /?add=me&days=%D9%A7 (U+0667) as a control (expect 200 with dur-7 checked).
4. Repeat the two failing GETs with raise_app_exceptions=True to capture the exception type and the whitelister frames of the traceback.
5. Anonymous chain on a fresh app: without a session GET /?add=me&label=<65 x 'a'> (expect 303 to /login?next=...), GET that login page and confirm the hidden next field echoes the path, POST /login with password and next=<crafted path> (expect 303 to the crafted path), then GET that location.
6. Operator variant: GET / for a CSRF token, POST /invites (Origin/Sec-Fetch-Site same-origin) with name of 65 characters and otherwise valid fields; then with 64 characters as the boundary control.
7. Confirm GET / afterwards is 200 with headers and store.count() == 0 (no state effect); check safe_next with a 512- and a 513-character next to confirm the length gate.

Payloads:
- `GET /?add=me&label=aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa  (65 x 'a')`
- `GET /?add=me&days=%C2%B2  (U+00B2 SUPERSCRIPT TWO)`
- `GET /login?next=%2F%3Fadd%3Dme%26label%3Daaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa  (what the anonymous 303 produces; the operator logs in from here)`
- `POST /invites  name=<65 x 'n'>&access_days=14&link_days=14&max_addresses=3&_csrf=<valid>  (operator-only variant)`

**Conditions.**
- authentication_level: The failing render happens in an operator session (logged in). The crafted URL can be produced and delivered by an anonymous party; an unauthenticated GET of it only yields the 303 to /login?next=... (verified: the 303 carries the security headers).
- user_interaction: The operator must open the crafted link (and log in from it if not yet logged in) or hand-edit the URL / invite POST themselves; the rendered form cannot produce the input because of maxlength=64.
- data_state: No stored state is required or changed; the effect is one failed response per crafted request and the app keeps serving.

**Actual result.** Primitives: normalize_label('a'*65) raised ValidationError key=error.label_too_long params={'max': 64} (isinstance ValueError True); normalize_label('a'*64) accepted; '\u00b2'.isdigit()=True, isdecimal()=False, int('\u00b2') -> ValueError "invalid literal for int() with base 10: '²'"; '\u0667'.isdigit()=True and int()=7; duration_presets=(1, 7, 14, 30). Logged in: GET /?add=me&days=7&label=Laptop -> 200 with all four headers, value="203.0.113.9", dur-7 checked, value="Laptop". GET /?add=me&label=<64 a> -> 200 with headers. GET /?add=me&label=<65 a> -> 500 body 'Internal Server Error', all four headers absent. GET /?add=me&days=%C2%B2 -> 500, headers absent. GET /?add=me&days=%D9%A7 -> 200 with headers, dur-7 checked. GET / afterwards -> 200 with headers, store.count()=0. With raise_app_exceptions=True: whitelister.entries.ValidationError: error.label_too_long with frames app.py:87 dispatch -> app.py:492 index -> app.py:267 prefill_from_query -> entries.py:35 normalize_label; builtins.ValueError invalid literal for int() with frames app.py:87 dispatch -> app.py:492 index -> app.py:265 prefill_from_query. **Impact.** One request fails with a bare 500 that lacks the security headers (static plaintext body, so the missing headers are inert) and an unhandled traceback is logged; the process keeps serving, no entry or invite is written, and the operator recovers by loading / again. No confidentiality or integrity effect; borders on informational and is a robustness defect in an anonymous-reachable input path rather than an exploitable weakness.

**Priority rationale.** Likelihood low: Requires the operator to open a crafted link (or craft the URL/request themselves); the rendered form cannot produce the input because of maxlength=64. The anonymous delivery path via /login?next= is straightforward but interaction-dependent, and only the operator session ever reaches the failing code. Impact low. Overall low. Confidence high: Every trace line was re-read in source at 4ce6e0d and both branches were independently reproduced in a sandboxed in-process harness against the pinned dependencies (Starlette 1.10.0, FastAPI 0.162.0, httpx 0.28.1) with exception types and whitelister frames captured; the anonymous next-link chain and the operator /invites variant were reproduced end to end, and the boundary controls (64 chars, U+0667, 512/513-char next) behave as the source predicts.

**Smallest source fix.** Make prefill best-effort for all three values so prefill_from_query can never raise: guard the days parse with str.isdecimal()/isascii() (or try/except ValueError) and fall back to None, and catch ValidationError from normalize_label (fall back to an empty label). Move create_invite's normalize_label into a try and flash the ValidationError via redirect_with_flash like add_entry does. Optionally register a catch-all exception handler so that any future unhandled error still passes through SecurityHeadersMiddleware. Add regression tests for a 65-character label, days=%C2%B2 and a 65-character invite name expecting 200/303 with the security headers.

### LOW — Unlimited free invite renewals let a link holder trigger one BunkerWeb cache-delete/refresh per request and wipe the operator's on-page history

Fingerprint: `whitelister/app.py:invite_redeem/refresh_after_change:unthrottled-known-address-renewal`

**Source location.** invite_redeem (app.py:725-751) treats a renewal of an already-active address like a list change: it unconditionally calls store.event_add and refresh_after_change (app.py:746-747); the request-time refresh path (app.py:316-325, bunkerweb.py:115-134) has no debounce or rate limit (the debounce lives only in Syncer._run, bunkerweb.py:224-225); and successful redemptions are never throttled or budgeted (open_invite records only failures, app.py:688-695; the known-address branch skips the budget check, app.py:736-738).

**Lower-trust principal.** Anyone holding an invitation link, after one normal redemption, repeats POST /i/<token> from the same address with a plain HTTP client (no cookies, no Origin or Sec-Fetch-Site headers).

**Bounded reproduction (target-native).**
1. Build the app in-process as tests/conftest.py does: EntryStore(':memory:'), BunkerWebClient whose httpx client is an httpx.MockTransport that records calls and answers 200 to DELETE /cache/..., with env WHITELISTER_PASSWORD, SESSION_SECRET (40 chars), TRUSTED_PROXIES=10.0.0.0/8, COOKIE_SECURE=no, BW_API_URL=http://bw-api:8888, BW_API_USERNAME/BW_API_PASSWORD dummies, WHITELIST_URL=http://whitelister:8080/ips.txt, SYNC_DEBOUNCE_SECONDS=3, TZ=UTC.
2. As the operator (ASGI peer 10.0.0.5, X-Forwarded-For 203.0.113.1) log in, add three entries (POST /entries with duration=7), create an invite (POST /invites) and read the token from the link shown on the page.
3. As a guest (peer 10.0.0.5, X-Forwarded-For 203.0.113.77, no Origin/Sec-Fetch-Site) POST /i/<token> once, then 250 more times; record each status.
4. Count fake bw-api calls recorded during the 250 renewals by method/path, compare store.active_networks before and after, read the events table and store.events_recent(5), and the invite's used/max_addresses.

Payloads:
- `POST /i/<token> HTTP/1.1 (no body, no cookies, no Origin/Sec-Fetch-Site) repeated 250 times from an address that already redeemed the link`
- `check_renewals.py (sandbox): operator login -> 3 entries -> POST /invites name=Tax advisor access_days=7 link_days=14 max_addresses=3 -> guest 203.0.113.77 POST /i/<token> once, then 250 more times`

**Conditions.**
- authentication_level: Possession of an open invitation link (no password or session); the first POST from the address consumes one budget slot, every later one from that address is free.
- system_configuration: BW_API_URL and WHITELIST_URL configured (otherwise refresh_after_change / trigger_refresh return early and only the history eviction remains).
- third_party_dependency: The cost on the BunkerWeb side (job re-run, configuration regeneration, instance reload per cache delete) is taken from the client's own documentation and was not observed locally; the compose example's 'DELETE /cache* 30r/m' limit would turn the excess into non-2xx responses surfaced as an API error to the operator.

**Actual result.** Sandbox run (v3-7, SYNC_DEBOUNCE_SECONDS=3): operator setup produced 4 history rows (3 add, 1 invite_create) and 4 bw-api calls; first guest redemption HTTP 200 and added 203.0.113.77 to the active list; the 250 renewals returned {200: 250} (no 429, no 403) and caused exactly 250 outbound DELETE /cache/global/whitelist/whitelist-download/<sha1>.list calls (one per request, no coalescing); the active network set never changed during the renewals; the events table held 200 rows, all invite_refresh, 0 of the operator's 4 rows survived and events_recent(5) showed five guest renewals; invite budget used stayed 1 of 3; client.status last_error=None.

**Impact.** Observed locally: one outbound bw-api cache delete per request without debounce and complete eviction of the operator's on-page history (the stdout audit log keeps the full record). The BunkerWeb-side reload cost per delete is documented in the client but was not observed; the compose example's API rate limit bounds it to 30 deletes/min and surfaces the overflow as an API error to the operator.

**Priority rationale.** Likelihood medium: Invitation links are meant to be pasted into messengers and shared among colleagues; any holder can script the POST (no browser headers or cookies needed) and the renewal is explicitly free, so neither budget nor throttle stops it. Impact low. Overall low. Confidence high: The source path is straight-line (no limiter on successes, unconditional event_add and immediate trigger_refresh), and the bounded sandbox harness reproduced the 1:1 request-to-DELETE ratio and the history eviction deterministically.

**Smallest source fix.** Make renewals cheap and bounded: when the address's entry is already active, do not call refresh_after_change or event_add (the content of /ips.txt is unchanged); route any invite-caused refresh through the debounced Syncer (syncer.request_refresh()) instead of the immediate client call; and enforce a minimum interval between renewals of the same address using invite_addresses.last_at (a new setting, e.g. INVITE_RENEW_MINUTES, or a fixed constant) or count successful redemptions against a small per-key limiter in addition to the failure throttle. Regression tests: redeem twice from one address and assert at most one bw-api DELETE and one history event per actual list change; renew 50 times and assert the operator's history rows survive and the fake bw-api saw no additional DELETE.

### LOW — Invite redemption silently shortens and re-attributes an operator-managed whitelist entry for the same network

Fingerprint: `whitelister/app.py:invite_redeem:upsert-overwrites-operator-entry`

**Source location.** whitelister/app.py:736 computes known only from store.invite_addresses(invite.id), never from store.find(net); app.py:739-741 then computes expires = now + access_days and calls store.upsert(net, invite.name, expires, now, created_by='invite:<name>') for any redeemer network; whitelister/entries.py:246-250 (ON CONFLICT(network) DO UPDATE SET label = CASE WHEN excluded.label = '' THEN entries.label ELSE excluded.label END, expires_at = excluded.expires_at, created_by = excluded.created_by) replaces the existing row with no ownership, expiry or attribution check anywhere on the path.

**Lower-trust principal.** A link holder (or the operator testing a link) connects from an address the operator has already whitelisted permanently, opens the link (page says 'Press the button and this connection is unlocked for 14 days', not 'already unlocked') and presses the button. The permanent grant becomes a 14-day grant labelled with the invite name and attributed to 'invite:<name>'; when it lapses, the whole network loses its whitelisting.

**Bounded reproduction (target-native).**
1. Build the app in-process (create_app(load_settings(), store=EntryStore(':memory:')) with BW_API_URL unset, TRUSTED_PROXIES=10.0.0.0/8, COOKIE_SECURE=no, a dummy WHITELISTER_PASSWORD and SESSION_SECRET) and drive it through httpx.ASGITransport clients whose TCP peer is 10.0.0.5.
2. As the operator (X-Forwarded-For 203.0.113.9): POST /login, read the _csrf value from GET /, POST /entries for 198.51.100.77 (duration=forever), 198.51.100.78 (duration=365) and 2001:db8:1:2::/64 (duration=forever), then POST /invites (access 14 days, max_addresses 0) and read the token from the once-shown link on GET /.
3. Record store.find(<network>) (label, expires_at, created_by) for each seeded network.
4. As a guest (X-Forwarded-For 198.51.100.77, then 198.51.100.78, then 2001:db8:1:2:abcd::1): GET /i/<token> and note the state text, then POST /i/<token> with Origin http://wl.example and Sec-Fetch-Site same-origin.
5. Read store.find(<network>) again and compare; list invite_addresses for the invite and the events table.

Payloads:
- `operator state: POST /entries network=198.51.100.77 label='Office NAT (forever)' duration=forever (also 198.51.100.78 label='Branch (365 d)' duration=365 and 2001:db8:1:2::/64 label='Office v6 (forever)' duration=forever)`
- `operator state: POST /invites name='Tax advisor' access_days=14 link_days=14 max_addresses=0 -> link http://wl.example/i/<token> shown once on GET /`
- `guest request from 198.51.100.77 (X-Forwarded-For via trusted proxy peer 10.0.0.5): GET /i/<token>, then POST /i/<token> with headers Origin: http://wl.example, Sec-Fetch-Site: same-origin, empty body`

**Conditions.**
- authentication_level: The lower-trust principal holds an open invitation link (anyone the operator sent it to, or anyone it was forwarded to); no login is needed.
- data_state: The whitelist already contains an operator-managed entry whose network text equals the redeemer's mapped network (bare IPv4 address, or exactly the /64 for IPv6), e.g. an office NAT address listed 'forever' or for 365 days.
- network_routing: The link holder connects from that network, e.g. the operator testing their own link from the whitelisted office, or a colleague/contractor opening a shared link from an already whitelisted site.

**Actual result.** check-1.txt (sandbox, 2026-11-08): all three GETs returned 200 in state 'ready' (not 'known'); all three POSTs returned 200 'done'. 198.51.100.77: before label='Office NAT (forever)' expires_at=None created_by='203.0.113.9'; after label='Tax advisor' expires_at=2026-11-22 14:48:09+00:00 created_by='invite:Tax advisor'. 198.51.100.78: expires_at 2027-11-08 -> 2026-11-22, label and created_by replaced. 2001:db8:1:2::/64 (guest 2001:db8:1:2:abcd::1): expires_at None -> 2026-11-22, label and created_by replaced. The entries table holds only the rewritten rows; invite_addresses lists all three networks; the events table holds the operator's three 'add' events (original labels, no expiry) followed by three 'invite_redeem' events. No outbound call was made (bw-api client disabled).

**Impact.** Integrity/availability of operator state only: a permanent or long whitelist grant for one network is silently cut to the invite period and loses its label and attribution; the network later drops off the list unexpectedly. No new access is gained beyond what the link already grants, and only the redeemer's own network is affected.

**Priority rationale.** Likelihood medium: Needs an open link and a redeemer whose address (or exact /64) is already an operator entry; this coincides with ordinary situations such as the operator testing their own link from the permanently whitelisted office address, or a colleague on an already whitelisted site opening a shared link. No tooling: one button press, and the page gives no hint. Impact low. Overall low. Confidence high: Complete source trace from the handler (app.py:736-741) to the ON CONFLICT clause (entries.py:246-250), no compensating control on the path, and an independent deterministic in-process reproduction in the sandbox for IPv4 forever, IPv4 365-day and IPv6 /64 operator entries seeded through the native POST /entries form.

**Smallest source fix.** Before writing, look up the existing entry for the redeemer's network. If one exists, is not expired and its expiry is later than (or endless compared to) now + access_days, keep it: record the touch so the address counts as known for this link, do not change expires_at, label or created_by, and render the 'known' state with the existing expiry. Only extend when the invite period ends later than the existing grant, and keep the existing label in that case. Mirror the same store.find lookup in invite_page so such an address is shown as already unlocked. Add a regression test: seed a forever operator entry for the guest's address, redeem, assert expires_at is still None and label/created_by unchanged; repeat with a 365-day entry and an IPv6 /64.

### LOW — Anonymous unknown-token requests from a handful of addresses lock every invitation link for all holders (shared process-wide throttle budget on /i/{token})

Fingerprint: `whitelister/app.py:open_invite/invite_throttle:global-budget-shared-lockout`

**Source location.** app.py:119 constructs invite_throttle = LoginThrottle(settings.login_max_failures, settings.login_lock_seconds) with the default global_budget=30 (security.py:148). record_failure (security.py:184-189) counts failures from all keys in one 60 s window and sets _global_until once the count exceeds the budget; retry_after (security.py:162-166) returns max(_global_until, own_until) so the lock applies to every key, and open_invite (app.py:688-689) refuses with 429 before looking the token up. The accounting dimension that decides the lock (the aggregate of all clients' failures) is attacker-influenceable with a small number of addresses, and the app runs a single uvicorn process so process-wide means service-wide.

**Lower-trust principal.** Anonymous internet client with ~11 source addresses (or one IPv6 /56) and no credentials or link.

**Bounded reproduction (target-native).**
1. Run the app in-process (httpx.ASGITransport, TRUSTED_PROXIES=10.0.0.0/8, trusted-proxy peer 10.0.0.5, X-Forwarded-For selects the client address; no BW_API_URL).
2. Log in as the operator and create one invitation; keep the link's token.
3. From an untouched address (198.51.100.90) GET /i/<token>: expect 200.
4. From each of 11 distinct source addresses (192.0.2.1 .. 192.0.2.11) send three GET /i/<unknown 34-char token> requests (33 total) within one minute.
5. From the untouched IPv4 address and from an untouched IPv6 address GET /i/<token> and POST /i/<token>: observe the status and whether a whitelist entry for that address was created.

Payloads:
- `GET /i/<34-char unknown token> repeated 3 times from each of 11 distinct source addresses (33 requests) within one minute`
- `GET /i/<valid token> and same-origin POST /i/<valid token> from an untouched address immediately after`

**Conditions.**
- network_routing: Attacker controls at least 11 distinct throttle keys per minute (IPv4 addresses, or IPv6 /64s - a single /56 gives 256) reaching /i/ directly or through the trusted proxy; sustained lockout needs fresh keys as per-key locks escalate (roughly 190 keys per hour).
- system_configuration: Default LOGIN_MAX_FAILURES=3 and hard-coded global budget 30/min; /i/ reachable without authentication as the README requires; single uvicorn process so the budget is service-wide.
- data_state: At least one open invitation whose holder tries to open or redeem it during the lock.

**Actual result.** I reproduced this in the sandbox. Statuses for the 33 attacker requests: 31x404 then 2x429 (the 31st failure trips the shared budget; the 32nd and 33rd are refused with 429 before any lookup). The untouched legitimate holder 198.51.100.90 afterwards got GET=429 (body 'too many attempts, try again later') and POST=429, and no whitelist entry was created for it. An untouched IPv6 holder (2001:db8:ffff::1) got GET=429. Operator /login from a fresh address still returned 303 (separate LoginThrottle instance). A pure LoginThrottle model with the same inputs gave retry_after(fresh key)=61 s right after the 33 failures from 11 keys and 0 s at +61 s, matching automatic 60 s recovery.

**Impact.** Denial of the invitation view/redemption feature only: existing whitelist entries, the operator UI, operator login and /ips.txt are unaffected; recovery is automatic 60 s after the attacker stops, as observed.

**Priority rationale.** Likelihood low: Requires no credentials and only ~31 cheap requests per minute, but at least 11 distinct addresses or IPv6 /64s per minute and a growing pool over time because locked keys cannot add failures; the attacker must also know or guess that the target runs this app with /i/ exposed. Impact low. Overall low. Confidence high: Complete source trace plus a bounded in-process reproduction showing legitimate holders from untouched IPv4 and IPv6 addresses receiving 429 on GET and POST after 33 unknown-token failures from 11 addresses, with operator login unaffected and automatic 60 s recovery confirmed by the LoginThrottle model.

**Smallest source fix.** Do not apply the process-wide failure budget to invitation lookups: the budget protects password-hash CPU, which the token path does not spend (SHA-256 + indexed lookup), and token entropy (192 bits) already makes guessing infeasible. Make global_budget optional in LoginThrottle and build invite_throttle without it, keeping the per-address / per-/64 exponential lockout. Regression test: 33 unknown-token requests from 11 addresses must leave GET/POST /i/<valid> from a twelfth address at 200.

### LOW — Operator removal of an invite-created entry does not stick: the stale invite_addresses row lets the removed redeemer re-list itself past an exhausted budget, logged as a renewal

Fingerprint: `whitelister/entries.py:EntryStore.delete:invite_addresses-stale-known-readd`

**Source location.** Two tables describe one lifecycle fact. `entries` is the source of truth for 'is this network listed', while `invite_addresses` is a redemption history that invite_redeem (whitelister/app.py:736-738) treats as an authorization shortcut: known => skip the budget gate and classify the write as a refresh. EntryStore.delete (whitelister/entries.py:268-271) and delete_entry (whitelister/app.py:608-620) neither tombstone nor consult the redemption history, and invite_redeem never checks that a known address is actually still listed (store.find(net) is used only on the GET side for display, whitelister/app.py:721). invite_touch_address (whitelister/entries.py:392-404) then reports the re-add as not new because its UPDATE hits the stale row.

**Lower-trust principal.** A guest who was unlocked via a shared invitation link and whose address the operator then removed from the whitelist; the guest still has the link and simply opens it again from the same connection.

**Bounded reproduction (target-native).**
1. Operator: log in, create an invitation (name 'Tax advisor', access 14 days, link 14 days, addresses 1) and copy the /i/<token> link shown once.
2. Guest A (198.51.100.77): POST /i/<token> with same-origin headers -> 200; an entry for 198.51.100.77 exists with created_by 'invite:Tax advisor' and a 14-day expiry.
3. Guest B (198.51.100.78): POST /i/<token> -> 409 (budget exhausted), no entry.
4. Operator: POST /entries/<id of A>/delete with the page CSRF token -> 303 and the 'was removed' flash; store.find(198.51.100.77) is None, but GET / still shows '1 of 1 addresses used' with 198.51.100.77 listed under the invite.
5. Guest A: GET /i/<token> -> 200 with lead 'This connection is already unlocked until . Press the button to start the period again.' and button 'Renew my access'; then POST /i/<token> -> 200 'valid until ...'.
6. Observe: entry for 198.51.100.77 exists again (new id) with a fresh 14-day expiry, a bw-api cache drop is issued and /ips.txt serves the address; history shows 'invite_refresh' after 'delete'; the audit event has new_address=false; the invite stays 1/1 (remaining 0); Guest B's POST still gets 409.

Payloads:
- `GET /i/<token> from the removed address (198.51.100.77 in the local check)`
- `POST /i/<token> with headers Origin: <app origin>, Sec-Fetch-Site: same-origin and an empty body, from the removed address`

**Conditions.**
- data_state: An invitation link that is still open (not revoked, valid_until in the future) and an entry created through it that the operator has deleted via POST /entries/{id}/delete.
- network_routing: The removed visitor connects again from the same IPv4 address or the same IPv6 /64 (redeemer_network), i.e. the identity the operator just removed, as seen by the app through its trusted proxy.
- authentication_level: No login: the actor is the anonymous holder of the (possibly shared) link, a lower-trust principal than the operator who performed the removal.

**Actual result.** Sandboxed ASGITransport run (fake bw-api via httpx.MockTransport, in-memory store, scratch file check-1-v3-8-delete-readd.txt): 'A POST: 200 | entry: (1, invite:Tax advisor, 14.0)'; 'B POST (budget 1 exhausted): 409 | entry B: None'; 'operator delete: 303 | was removed flash: True | store.find A: None'; 'index after delete shows 1 of 1 addresses used: True | .77 still listed under invite: True'; 'invite_addresses rows after delete: [{invite_id: 1, network: 198.51.100.77}]'; 'active list after delete: []'; 'A GET after delete: 200 | lead: This connection is already unlocked until . Press the button to start the period again. | button: True'; 'A POST after delete: 200 | valid until in page: True'; 'entry re-created: (2, invite:Tax advisor, 14.0)'; 'bw cache drop issued on re-add: [(DELETE, /cache/global/whitelist/whitelist-download/b563f953e7c6fe56e62dd212cad4d10b4449d80f.list)]'; 'active list after re-add: [198.51.100.77]'; 'history newest-first: [(invite_refresh, 198.51.100.77), (delete, 198.51.100.77), (invite_redeem, 198.51.100.77), (invite_create, )]'; 'invite used/max after re-add: 1 / 1 remaining: 0'; 'B POST after A re-add: 409 | entry B: None'; '/ips.txt: 200 # bunkerweb-whitelister\n198.51.100.77\n'; audit lines: invite.redeem new_address=true, entry.delete network=198.51.100.77, invite.redeem new_address=false.

**Impact.** The anonymous link holder regains, for the full access period, the BunkerWeb bypass the operator explicitly removed, past an exhausted budget, and the audit log and history mislabel it as a renewal; however the address is one the operator originally admitted through that link, no other address gains access, and the operator can still stop it by revoking the whole link.

**Priority rationale.** Likelihood medium: No guessing or special position is needed: the removed guest already holds the link and re-opening it is the natural reaction to losing access; the only precondition is that the link is still open, which is the normal state for a shared link whose other users are still welcome. Impact low. Overall low. Confidence high: Complete source lineage (delete -> stale invite_addresses -> known shortcut -> upsert -> refresh classification) verified line by line, and an independent sandboxed in-process run with the project's own fixture pattern reproduced every step deterministically, including the budget bypass for the exhausted link and the new_address=false audit line.

**Smallest source fix.** Make the redemption history agree with the entry lifecycle. When the operator deletes an entry, mark (do not delete, so the slot stays consumed) the matching invite_addresses rows as removed, and have invite_page/invite_redeem refuse a removed address while the removal stands (or, if re-admission is wanted, treat it as a new unlock: run the budget gate and make invite_touch_address report it as new). Do not derive `known` from invite_addresses alone: require store.find(net) to exist as well, otherwise the normal budget path and new_address=true audit apply. Note that only checking store.find is insufficient on its own because invite_touch_address's UPDATE would still hit the stale row and return False. Regression test: invite with max_addresses=1, redeem, operator delete, second GET from the same address must not render the 'already unlocked' state with an empty date, and a second POST must not re-create the entry (or must be counted and logged as a new unlock).

### Positive source patterns

- Hash-pinned dependencies with `--require-hashes`; pip-free runtime venv; non-root uid 10001; read-only, cap-dropped compose example; GHCR push gated to main/v* tags; tag must equal `__version__`.
