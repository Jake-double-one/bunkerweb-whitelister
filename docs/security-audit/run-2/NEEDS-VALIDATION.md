# Needs validation (prioritised leads, no severity)

## Compose example multi-homes the whitelister and BunkerWeb on bw-universe without a fixed address, so proxied requests can arrive from a peer outside TRUSTED_PROXIES and collapse every client identity onto the proxy

Fingerprint `docker-compose.example.yml:whitelister:dual-network:bunkerweb-unpinned-on-bw-universe-outside-TRUSTED_PROXIES`

docker-compose.example.yml (the file README.md:102 starts in the quick start) attaches the whitelister to bw-services (10.20.30.0/24) and bw-universe (10.20.40.0/24) and sketches BunkerWeb and bw-scheduler on the same two networks, but pins BunkerWeb only on bw-services (ipv4_address 10.20.30.2) and leaves its bw-universe address dynamic. .env.example sets TRUSTED_PROXIES=10.20.30.2/32 and LIST_ALLOWED_NETWORKS=10.20.30.0/24, i.e. only the bw-services side. Because the whitelister has an address on both networks, a lookup of `whitelister` from a container that shares both networks can resolve to its bw-universe address, so BunkerWeb's REVERSE_PROXY_HOST=http://whitelister:8080 or the scheduler's WHITELIST_IP_URLS download may connect over bw-universe from an unpinned 10.20.40.x source. Re-derived in the sandbox (app built from TRUSTED_PROXIES=10.20.30.2/32, LIST_ALLOWED_NETWORKS=10.20.30.0/24, dummy secrets, no BW_API_URL): security.py:254-255 returns (peer, False) for peer 10.20.40.3, so GET /login renders 10.20.40.3 as the visitor while peer 10.20.30.2 renders the forwarded 203.0.113.5; three wrong passwords from three different forwarded clients via peer 10.20.40.3 lock the shared key and the fourth client gets 429, whereas via the trusted peer each client keeps its own key (401 x4); POST /i/<token> via peer 10.20.40.3 whitelists 10.20.40.3 (accepted because ALLOW_PRIVATE=yes in .env.example) and records it as the invite's address instead of 203.0.113.5; GET /ips.txt with the correct token returns 200 from 10.20.30.9 and 403 from 10.20.40.9. Identity spoofing stays impossible (fail-closed), but whenever the bw-universe path is chosen: any anonymous visitor can lock the login and invite throttles for everyone (LOGIN_MAX_FAILURES=3, within the 6r/m /login limit), audit/history actors become the proxy's internal address, invitation redemption and add=me grant the proxy's internal address instead of the visitor's (the invitee receives no access), and the scheduler's list download is refused so the list goes stale. Whether Docker's embedded DNS and BunkerWeb 1.6.17's nginx actually route proxy or scheduler traffic over bw-universe, and whether the owner's real stack keeps this attachment (the compose file itself says the BunkerWeb services are only sketched, lines 2 and 45), is not visible in source.

**Claimed root cause.** docker-compose.example.yml:18-20 attaches the whitelister to bw-universe as well as bw-services, and docker-compose.example.yml:50-53 pins BunkerWeb's address only on bw-services while leaving it unpinned on bw-universe (line 51); .env.example:15 and :24 therefore name only the bw-services address/subnet, so any proxy or scheduler connection that Docker's multi-network name resolution sends over bw-universe arrives from a peer that config.py:204 / security.py:254 do not recognise as the ingress.

## /ips.txt 'direct request' gate is a fixed five-header denylist that neither refuses TRUSTED_PROXIES peers nor treats the configured CLIENT_IP_HEADER as proxy metadata

Fingerprint `whitelister/app.py:ips_txt:direct-gate-ignores-trusted-proxies-and-client-ip-header`

GET /ips.txt (whitelister/app.py:404-415) serves the full active whitelist when the TCP peer parses, is inside LIST_ALLOWED_NETWORKS, the optional LIST_TOKEN matches, and none of exactly five lowercase header names (x-forwarded-for, forwarded, x-real-ip, x-forwarded-host, x-forwarded-proto; whitelister/security.py:275-276) is present. The gate never consults settings.trusted_proxies or settings.client_ip_header. In the shipped topology the BunkerWeb ingress (10.20.30.2, TRUSTED_PROXIES=10.20.30.2/32) lies inside LIST_ALLOWED_NETWORKS=10.20.30.0/24 (and inside the default, all private ranges), and REVERSE_PROXY_URL=/ publishes every path including /ips.txt through that ingress. Reproduced in the sandbox (httpx.ASGITransport, dummy secrets, no network): with LIST_TOKEN unset, a request whose peer is the trusted-proxy address 10.20.30.2 with no header, or carrying only via / x-forwarded-port / cf-connecting-ip / true-client-ip / x-forwarded-server, returns 200 and the list (including with CLIENT_IP_HEADER=CF-Connecting-IP and only cf-connecting-ip present); the same peer with any of the five recognised names returns 403; an outsider peer 203.0.113.9 returns 403; with LIST_TOKEN set the right token is required and token plus x-forwarded-for is still 403. The app's documented design (README.md:70-73) relies on the proxy always adding one of those header names, so whether an anonymous internet client can reach the 200 state through the published UI origin depends on BunkerWeb 1.6.17's generated proxy_set_header lines and on REVERSE_PROXY_HEADERS / CDN deployment choices that are not in the repository, and on whether the deployed LIST_TOKEN is set.

**Claimed root cause.** whitelister/security.py:275-276 implements the 'direct request' test as a denylist of five header names, and the gate at whitelister/app.py:410 does not additionally refuse peers inside settings.trusted_proxies (which never legitimately fetch the list; the scheduler does) nor treat settings.client_ip_header as a forwarding header, so the control depends on proxy header-insertion behaviour outside the application's own configuration rather than on the application's trust model.

### Source trace
1. `whitelister/app.py:404` (entrypoint, create_app.ips_txt): GET /ips.txt route; reachable from any peer able to open a TCP connection, including the BunkerWeb ingress that publishes the whole app (REVERSE_PROXY_URL=/)
2. `whitelister/app.py:407` (propagation, create_app.ips_txt): peer = parse_ip(request.client.host): the socket peer (uvicorn proxy_headers=False, whitelister/__main__.py:29-30); the trusted-proxy address is a valid peer
3. `whitelister/security.py:276` (propagation, has_forwarding_headers): any() over exactly five lowercase header names; settings.trusted_proxies and settings.client_ip_header are not parameters and are not consulted
4. `whitelister/config.py:230` (propagation, load_settings): LIST_ALLOWED_NETWORKS defaults to PRIVATE_NETWORKS (config.py:18-25), which contain the ingress; LIST_TOKEN (config.py:213) is optional (only the placeholder is rejected)
5. `whitelister/app.py:410` (propagation, create_app.ips_txt): single 403 gate: peer parses, has_forwarding_headers(headers) is False, in_networks(peer, settings.list_allowed_networks) and token_ok (line 409, constant-time compare); no trusted_proxies / client_ip_header check
6. `whitelister/app.py:415` (sink, create_app.ips_txt): PlainTextResponse with render_list(store.active_networks(now)): the full active whitelist; line 414 also records the fetch timestamp (meta list_fetched_at), so a foreign fetch moves the 'BunkerWeb last fetched' mark

### Verified evidence
- `whitelister/security.py:276`: has_forwarding_headers returns any(name in headers for name in (x-forwarded-for, forwarded, x-real-ip, x-forwarded-host, x-forwarded-proto)): a fixed denylist
- `whitelister/app.py:410`: /ips.txt gate combines peer parse, has_forwarding_headers, in_networks(list_allowed_networks) and the token only; settings.trusted_proxies and settings.client_ip_header are not referenced anywhere in ips_txt
- `whitelister/config.py:211`: CLIENT_IP_HEADER lets the operator declare a custom identity header (e.g. CF-Connecting-IP) that resolve_client_ip (security.py:237-272) treats as proxy metadata, but /ips.txt does not treat it as a forwarding header
- `whitelister/config.py:213`: LIST_TOKEN is optional: an unset or empty value means no token; only the .env.example placeholder is rejected
- `.env.example:15`: TRUSTED_PROXIES=10.20.30.2/32 names the BunkerWeb ingress
- `.env.example:24`: LIST_ALLOWED_NETWORKS=10.20.30.0/24 contains the ingress address 10.20.30.2
- `.env.example:26`: comment: leave LIST_TOKEN empty only if you accept subnet membership as the sole gate (line 27 ships a placeholder that must be replaced)
- `docker-compose.example.yml:40`: bunkerweb.REVERSE_PROXY_URL=/ publishes every path of the whitelister, /ips.txt included, through the BunkerWeb ingress pinned at 10.20.30.2 (line 53)
- `README.md:70`: documented design: /ips.txt answers only direct requests, where 'any forwarding header means came through a proxy'; the design therefore presumes the proxy always inserts one of the recognised names
- `whitelister/__main__.py:29`: uvicorn proxy_headers=False, forwarded_allow_ips=[]: request.client.host is the raw socket peer, so the app alone interprets forwarding metadata
- `tests/test_app.py:356`: existing tests cover allowed peer, XFF/Forwarded refusal, outsider refusal and the token, but no test covers a TRUSTED_PROXIES peer fetching the list without a recognised header or a configured CLIENT_IP_HEADER-only request

### Exact blockers
- BunkerWeb 1.6.17 reverse-proxy behaviour is not in the repository: whether the generated nginx server block for the whitelister service unconditionally sets X-Forwarded-For / X-Real-IP / X-Forwarded-Proto / X-Forwarded-Host on proxied requests, and whether REVERSE_PROXY_HEADERS (or a CDN front that supplies only a custom identity header such as CF-Connecting-IP) can leave all five recognised names absent, decides whether an anonymous internet client can reach the observed 200 state through the published UI origin
- Whether the deployed LIST_TOKEN is set is a deployment fact: the example ships a placeholder that must be replaced, but config.py:213, .env.example:26 and README.md:157 allow leaving it empty, in which case subnet membership plus the header denylist is the sole gate
